## Document model and sync (documented, E-FG-01)

Figma's engineering post "How Figma's multiplayer technology works" describes these:

- **The tree:** a document is a tree of objects (root, pages, page contents), each with an ID and properties. It is modelled as `Map<ObjectID, Map<Property, Value>>`.
- **Conflicts:** they are resolved **per property**. The server keeps the last value it received, a last-writer-wins register ordered by the server rather than by timestamps. Edits to different properties never conflict, and a concurrent text edit ends up as one client's whole value.
- **Server authority:** the server is authoritative. It rejects a parent change that would create a cycle, and clients briefly detach such objects until it decides.
- **Child order:** fractional indexes, positions strictly between 0 and 1. Parent and position are stored as one property, so they change together.
- **IDs:** clients create IDs with a per-client ID, so they can work offline.
- **Undo:** undo and redo are per client. The principle: undoing a lot, copying, and redoing back to the present leaves the document unchanged.
- **Offline:** a client edits offline. On reconnect it downloads the document and reapplies its edits.

**Inferred for Ninerr:** Ninerr's single-writer host with whole-transaction validation is stricter, and it suits a local-first, agent-heavy editor. Two ideas are worth taking if Ninerr adds live collaboration: property-level merge, and fractional child order.

## Editing model (documented, E-FG-02)

The Plugin API's node properties (developers.figma.com/docs/plugins/api/node-properties) name the editing vocabulary:

- **Auto Layout:**
  - `layoutMode` (horizontal or vertical);
  - `primaryAxisSizingMode` and `counterAxisSizingMode` (`FIXED` or `AUTO`);
  - `layoutSizingHorizontal` and `layoutSizingVertical` (fixed, hug, fill);
  - `itemSpacing`, padding on each side, and `layoutWrap` with `counterAxisSpacing` and `counterAxisAlignContent`;
  - `primaryAxisAlignItems` and `counterAxisAlignItems`;
  - `layoutPositioning` (absolute inside Auto Layout), `layoutGrow`, `layoutAlign`.
- **Constraints:** `constraints` pin a node relative to its containing frame.
- **Components:**
  - components, component sets (variants) and instances;
  - `componentPropertyDefinitions` (`BOOLEAN`, `TEXT`, `INSTANCE_SWAP`, `VARIANT`, `SLOT`), `componentPropertyReferences`, and `add`/`edit`/`deleteComponentProperty`.
- **Variables:** variables bound per field (`boundVariables`, `setBoundVariable`), in collections with modes (`explicitVariableModes`, `resolvedVariableModes`).

**Inferred:** Auto Layout is a *constrained subset of flexbox*, given a design vocabulary of hug, fill and fixed. It maps closely to CSS flex with `fit-content`, `flex: 1` and fixed sizes. That is the mapping Ninerr can adopt without a new layout engine.

## Agent interface (documented, E-FG-03 to E-FG-06)

- **Servers (E-FG-03).**
  - **Remote:** `https://mcp.figma.com/mcp`, recommended, with the broadest features.
  - **Desktop:** `http://127.0.0.1:3845/mcp`, from the desktop app, for some organization plans.
- **Tools (E-FG-04).** About 32 are listed.
  - **Read:** `get_design_context` (code-like context, React and Tailwind by default), `get_metadata` (a sparse XML outline), `get_screenshot`, `get_variable_defs`, `search_design_system`, `get_code_connect_map`, `get_libraries` and others.
  - **Write:** `use_figma`, `html_to_figma`, `generate_figma_design` (live web UI to layers), `upload_assets`, `create_new_file`, Code Connect mapping tools, and others.
- **Writing (E-FG-05).** `use_figma` lets the agent "run code in your Figma file through the Figma Plugin API".
  - **Undocumented:** the documentation states **no** atomicity, undo or versioning for these writes.
  - **Advice:** it advises testing "on a duplicate", keeping a backup, and working "in smaller steps, checking its work as it goes".
  - **Limits:** 20 KB of output per call; `use_figma` cannot add new images; fonts must be uploaded to the account.
  - **Status:** writing is in beta and needs a Full seat outside drafts.
- **Design context (E-FG-06).** `get_design_context` is "not designed to return production-ready code". It encodes the design so an LLM can read it, and the agent adapts it to the codebase. Code Connect maps components to real code components.

**Inferred:** writing to Figma through MCP is *arbitrary plugin code with a backup advisory*. Figma's own reliability guidance is behavioural (small steps, check your work), not transactional. A typed, atomic, revision-checked operation contract, as in Ninerr's existing history, is the safer design.

## Components, design systems and handoff (documented, E-FG-02, E-FG-06, E-FG-07)

- **Libraries:** published components, styles and variables are searchable by agents (`search_design_system`, `get_libraries`).
- **Code Connect (E-FG-07):** maps a design component to a code component in the user's framework, so generated code reuses real components.
- **Inferred:** Ninerr's code-component binding (`packages/design-components`: contracts, variants, drift detection) and its three-way code write-back cover the same need from the code side. They are not wired into the editor yet.

## Prototyping and motion (documented, E-FG-08)

- `get_motion_context` returns keyframe data and CSS or Motion snippets, so motion is part of what agents read.
- Prototype connections and transitions exist in the product. Their internals are **unknown** to this study.

## Performance and large documents (E-FG-09)

- No figure is documented in the pages read. Figma's renderer and memory model are **unknown** here.
- Tool output is capped (20 KB per call), and agents are steered to `get_metadata` as a cheap outline. **Inferred:** large-document agent work is bounded by summarization.

## What this means for Ninerr

- **Worth adopting, as Ninerr's own designs:**
  - the hug/fill/fixed sizing vocabulary over CSS flex;
  - constraints for absolutely placed layers;
  - components with typed properties (boolean, text, instance swap, variant, slot) and overrides;
  - variables with collections and modes;
  - a sparse structural outline tool for agents;
  - design-system search for agents;
  - component-to-code mapping, which Ninerr has the parts for.
- **Ninerr's stronger position:**
  - typed atomic transactions;
  - attributed undo;
  - person approval for destructive agent edits;
  - local-first persistence with crash recovery;
  - real HTML and CSS as the stored format, rather than a proprietary format;
  - code write-back with conflict detection.
